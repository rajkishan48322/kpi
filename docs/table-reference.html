4. KPA Bands

The marking-scale rows belonging to one KPA — reference only, never auto-applied to a real mark.

Structure

ColumnTypeRule
idbigintPRIMARY KEY
kpa_idbigintFOREIGN KEY → kpas.id, NOT NULL, ON DELETE CASCADE
labeltextNOT NULL — e.g. "At Target"
min_deltanumericnullable — NULL means open-ended floor
max_deltanumericnullable — NULL means open-ended ceiling
marknumericNOT NULL
sort_orderintNOT NULL, defaults to 0
Dependency: the parent KPA (kpa_id) must already exist — this is a child table. If the parent KPA is deleted, its bands are deleted automatically (CASCADE).

5. Employees

The central "hub" table — one row per person + role + KPA combination, not one row per person.

Structure

ColumnTypeRule
idbigintPRIMARY KEY
emp_codetextNOT NULL — e.g. EMP1001; not unique alone, since one person has multiple rows
nametextNOT NULL
department_idbigintFOREIGN KEY → departments.id, nullable (optional)
office_codetextoptional
role_idbigintFOREIGN KEY → roles.id, NOT NULL
kpa_idbigintFOREIGN KEY → kpas.id, NOT NULL
weightage_pctnumericNOT NULL, CHECK — between 0 and 100
start_datedateNOT NULL
end_datedateoptional
Table-level: UNIQUE (emp_code, role_id, kpa_id) — the same person can't have two identical role + KPA rows.
Trigger-enforced (not a plain constraint): every row sharing one emp_code — across all their roles — must have weightage_pct values that sum to exactly 100. Enforced by fn_check_employee_weightage_sum(), fired as a deferred constraint trigger: insert all of a person's rows in one transaction, or keep an existing row's percentage corrected so the running total is always 100 after each statement. An unbalanced total raises an error such as "Employee EMP1001 KPA weightages must sum to 100 across all roles (currently 80)".
